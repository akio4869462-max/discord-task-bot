# 競走馬育成へのゲーム要素刷新 — 設計方針

就活RPG（レベルアップ＋課題ボス撃破）を、**競走馬の育成とレース出走**へ置き換える。
ウイニングポストのように1頭を育てて出走させ、着順を競い、引退後は世代交代する。

## 1. 決定事項

| 論点 | 決定 | 理由 |
|---|---|---|
| 育成単位 | **1頭ずつ ＋ 世代交代あり** | 能力が上限に達した後も血統を介して続く。UIは1頭分で済み複雑化しない |
| レースを見る手段 | **静的HTMLの再生ビューア** | サーバ不要。結果JSONを読んでcanvasで再生。Artifactとして公開すればスマホからも見られる |
| ライバル馬 | **実データから生成した架空馬** | 実在馬名を持ち出さずに、実際の成績分布・脚質・血統傾向だけを反映できる |
| コード配置 | **discord-task-bot 内に同居**（`race_sim/`） | 既存の pytest / CI / デプロイにそのまま乗る |

## 2. 全体構成

```
race_sim/rivals.py     ライバル馬プールから出走表を組む
       |  出走表dict
       v
race_sim/engine.py     レースエンジン（純ロジック・標準ライブラリのみ・決定的）
       入力: 出走表dict + seed  →  出力: レース結果dict
                 |
       +---------+---------+
       |                   |
race_sim/viewer.html   horse_logic.py
  結果JSONを再生         厩舎データ管理・成長・出走登録・結果反映（Discord非依存）
                             |
                          ui_horse.py（Discord View/Modal）
```

依存の向きは一方通行。`engine.py` は誰にも依存せず、`horse_logic.py` が engine を呼ぶ。
既存の「`main.py` だけが discord を知る」原則をそのまま踏襲する。

### 実データ（keiba_score_search）の扱い

`keiba_score_search/data/all_utf8.csv` は 222MB あり、**このリポジトリには持ち込まない**。
向こうの venv（duckdb / pandas あり）でオフラインのバッチを回し、成果物として次の
小さいJSONだけを `race_sim/data/` にコミットする。

| 生成物 | 中身 | 概算サイズ |
|---|---|---|
| `course_baseline.json` | コース別の基準タイム85件、クラス補正、馬場補正、着差・脚質・人気別勝率の分布 | 15KB |
| `rivals.json` | 実成績の分布から生成した架空馬2,683頭（能力・位置取り傾向・適性・血統名） | 890KB |

⭕ Bot側の実行時依存は増やさない。`engine.py` が使うのは `random` / `math` / `json` だけ。

## 3. データ契約

3層が独立して開発できるよう、**JSONの形を先に固定する**。

### 3.1 厩舎データ `data/stable.json`

```jsonc
{
  "generation": 1,
  "current": {
    "id": "uuid",
    "name": "ウマの名前",
    "sex": "牡", "age": 3, "birth": "2026-09-09",
    "growth": { "speed": 135, "stamina": 0, "power": 0, "guts": 55, "wit": 8, "dash": 0 },
    "style": "先行",
    "aptitude": { "turf": "A", "dirt": "C", "sprint": "B", "mile": "A", "middle": "B", "long": "D" },
    "condition": 0,
    "class": "未勝利",
    "record": { "starts": 0, "win": 0, "place": 0, "show": 0, "prize": 0 },
    "pedigree": { "sire": "...", "broodmare_sire": "..." },
    "history": [{ "date": "2026-09-14", "race": "...", "pos": 3, "time": 95.2, "last3f": 34.6 }]
  },
  "retired": [],
  "stallions": []
}
```

`growth` は**活動の累積分数（生データ）**で持ち、能力値は読み出し時に導出する。
こうしておけば成長カーブを後から調整しても過去の記録が壊れない。

### 3.2 エンジン入力（出走表）

```jsonc
{
  "race": { "name": "...", "course": "東京", "surface": "芝", "distance": 1600,
            "cond": "良", "class": "1勝クラス", "field_size": 16 },
  "seed": 123456,
  "entries": [
    { "no": 1, "name": "...", "params": { "speed": 780, "stamina": 620, "power": 540,
      "guts": 600, "wit": 500, "dash": 700 }, "style": "差し", "aptitude": {...},
      "condition": 0, "is_player": false }
  ]
}
```

### 3.3 エンジン出力（結果）

```jsonc
{
  "race": { ... }, "seed": 123456,
  "horses": [
    { "no": 1, "name": "...", "finish": 3, "time": 95.2, "last3f": 34.6,
      "passing": [5, 5, 4, 3],
      "splits": [12.4, 11.0, 11.3, 11.6, 11.9, 12.1, 12.3, 12.6],
      "trouble": null, "comment": "直線で伸びた" }
  ]
}
```

⭕ 位置の時系列を0.1秒刻みで持つとJSONが数百KBに膨らむ。**200m区間ごとの通過タイム
（`splits`）だけを持ち、ビューア側で単調補間してアニメーションする**。エンジンはseedを
与えれば同じ結果を返すので、結果を保存しなくても再現できる。

## 4. 能力パラメータと活動の対応

1つの活動が1つの能力だけを育てる形にすると、活動を廃止した瞬間にその能力の供給源が
消える。実際に「📄 書類作成」を廃止したとき根性が宙に浮いた。**1活動＝複数能力**に
配分する（`horse_logic.ACTIVITY_PARAMS`。重みの合計は活動ごとに1.0）。

| 活動 | 育つ能力（配分） | 意味 |
|---|---|---|
| 💻 開発作業・集中タイマー | スピード 0.6 / 根性 0.4 | 巡航速度と、競り合ったときの減速抑制 |
| 📚 インプット・過去問演習 | 賢さ 0.7 / 根性 0.3 | ブレ幅の縮小・不利を受ける確率の低下 |
| 💪 筋トレ | スタミナ 0.5 / パワー 0.5 | 消耗耐性、ダート・重馬場補正 |
| ⌨️ タイピング訓練 | 瞬発力 0.7 / スピード 0.3 | 上がり3Fの伸び |
| 🔥 連続記録 streak | 調子（-2〜+2） | 途切れると下がる |
| ✅ タスク完了 | スピード 0.6 / 根性 0.4（開発相当の固定分） | 資金には入らない |

⭕ **「📄 書類作成」は廃止した。** 就活時に作った項目で、もう書類を書く機会がない。
   UI（厩舎の報告メニュー・タスクのカテゴリ）からは消したが、`ACTIVITY_PARAMS` には
   `'document': {'guts': 1.0}` を残してある。**古いタスクが完了されたときに落ちないため**で、
   新規に選ぶ手段は無い。

⭕ 筋トレとタイピングはRPG時代は記録が独立していた。ここで初めてゲームに接続され、
全機能が1つの育成ループに束ねられる。

⭕ まだ何も育てていない記録：体組成、タイピングのWPM計測、過去問の正答率、
   ニュースの新語。上達度を能力に乗せない方針（後述）の結果として浮いている。

内部のパラメータ名は `speed` / `stamina` / `power` / `guts` / `wit` / `dash` の6つ。
0〜1000のスケールで、**500が能力zスコアの0**にあたる。

クラスは 未勝利 → 1勝 → 2勝 → 3勝 → OP → G3 → G2 → G1。
**勝てば昇級**という形で、旧「課題ボス撃破」の役割を引き継ぐ。

### クラスと能力値の対応

較正の結果、クラスの強さは次の水準になった（`engine.CLASS_MEAN_Z`）。
育成カーブはこの表を目標に設計する。

| クラス | 平均能力z | パラメータ換算 |
|---|---|---|
| 未勝利 | -1.81 | 約 140 |
| 1勝 | -0.95 | 約 310 |
| 2勝 | -0.48 | 約 400 |
| 3勝 / OP | -0.02 | 約 500 |
| G3 | +0.14 | 約 530 |
| G2 | +0.38 | 約 580 |
| G1 | +0.88 | 約 680 |

⭕ デビュー時が約140、G1級で約680。上限1000（`ABILITY_CAP`）は「G1を大きく超える怪物」
   にあたり、最良の配合と育成で届く。同一クラス内のばらつきは z で 0.34（`FIELD_Z_SD`）。

### 成長カーブ（確定・2026-09-11に難易度を見直し）

**能力 = 140 + 3.5 × (その能力に積んだ分)^0.70**（上限1000）

⭕ **「配合も育成もかなり上手くやって、G1を7勝」を狙う。** G1へは7勝で昇級するので、
   最良の馬は序盤の下級条件をほぼ勝ち切って10戦目前後でG1に上がり、残りのG1で勝率6割超、
   合計14勝前後になる。当初の係数 6.968（50時間でG1級）では**週4時間の記録でもG1に到達
   して15勝**し、普通の週と最良の差が無かった。係数を振ってシミュレーションした結果
   （各16頭、20戦、中央値）：

| `GROWTH_K` | 普通（週4h・配合なし） | 良い（週9h・配合なし） | 最良（週14h＋最良の配合） |
|---|---|---|---|
| 6.968（旧） | 16勝 | 18勝 | 19勝 |
| 4.5 | 9.5勝・G1 2.5勝 | 13勝・G1 6勝 | 17勝・G1 10勝 |
| 4.0 | 8勝・G1 1勝 | 10勝・G1 3勝 | 15勝・G1 8勝 |
| **3.5** | **6勝・G1 0勝** | **8勝・G1 1勝** | **14勝・G1 7勝**（4〜9） |
| 3.0 | 5勝・G1 0勝 | 7勝・G1 0勝 | 11勝・G1 4勝 |

   3.5 で「普通の週ではG1を勝てない／良い週でたまに1勝／最良で7勝」の階段になる。
   上限1000は最良でようやく届く水準（最終能力928）なので、そのまま残す。

| クラス | 能力 | 1能力あたり | 6能力ぶんの合計 |
|---|---|---|---|
| 未勝利 | 140 | — | — |
| 1勝 | 310 | 4.3h | 25.7h |
| 2勝 | 400 | 7.8h | 47.1h |
| 3勝 / OP | 500 | 12.5h | 74.9h |
| G2 | 580 | 16.6h | 99.8h |
| G1 | 680 | 22.3h | 133.7h |
| 上限 | 1000 | 43.3h | 260.0h |

### 想定ペースと開催頻度

20戦で引退・週2開催なので、1頭の現役期間は10週（約2.3か月）。実時間11.5h/週
（開発6h・インプット3h・筋トレ5回・タイピング5回）は回数制の換算（後述）で
**換算19h/週**になる。

| | 能力（均等に積んだ場合） |
|---|---|
| 2週目 | 364（1勝〜2勝） |
| 5週目 | 565（G2） |
| 10週目＝引退 | 831（G1平均680の上） |
| 最良の配合（両親1000・価値1.5）の上積み | +390分/能力 → デビュー時 368 |
| 最良の配合 ＋ 10週 | 927 |

⭕ **育成だけでG1平均に届くのは7週目（134時間）。** そこから上限1000までの260時間は
   1世代では積めず、配合の上積みが乗ったときに初めて近づく。G1で勝ち続ける馬は
   世代を重ねないと作れない。

⭕ **開催は土曜と水曜の週2で確定。** 週1開催（20週）にすると成長が進みすぎて後半が
   消化試合になる。年5〜6世代回るので、配合の土台としても釣り合う。

⭕ 土日ではなく**土曜と水曜**にするのは間隔のため。土日だと2戦が24時間以内に固まり、
   その間に積める時間がほぼゼロなので、2戦目が1戦目とほぼ同じ状態の馬で走ることになる。
   土曜→水曜（4日）→土曜（3日）ならどちらの間隔にも成長が乗り、2戦が別の意味を持つ。

⭕ **昇級には勝利が要る**（G1まで最低7勝）。普通の週では6勝前後なので、多くの世代は
   G2〜G1の入り口で現役を終え、G1は勝てない。そこから上へ行くには配合で初期値を積む。

⭕ 上限に達したぶんの努力は捨てない。**余剰は引退後の種牡馬・繁殖牝馬としての価値に
   回す**（次世代の初期能力が上がる）。走り切った馬に注いだ時間が次の代に残る。

### 時間を記録していない活動の換算

筋トレとタイピングは実施日しか記録していない（分を持たない）ため、回数で換算する。

| 活動 | 1回あたり | 定数 |
|---|---|---|
| 💪 筋トレ 1セッション | **60分相当** | `horse_logic.TRAINING_MINUTES` |
| ⌨️ タイピング 1ドリル | **60分相当** | `horse_logic.TYPING_MINUTES` |

⭕ 上達度（WPMの伸びや体組成の変化）は能力に乗せない。計測が飛ぶと成長が止まるうえ、
   体重の増減をどう解釈するかという厄介な判断が要る。「やった回数」だけを見る。

⭕ **この60分は実際の所要時間（どちらも15分程度）とは切り離した「ゲーム上の価値」。**
   開発作業は週に数時間単位で記録されるのに対し、筋トレは週5回×15分＝75分しか入らない。
   この5〜10倍の時間差は `ACTIVITY_PARAMS` の重みをどう配分しても埋まらない。
   実際の1週（開発6h・インプット3h・筋トレ5回・タイピング5回）で4週走らせた結果：

| 1回あたり | スピード | 根性 | 賢さ | 瞬発力 | スタミナ | パワー | 最大/最小 |
|---|---|---|---|---|---|---|---|
| 15分（変更前） | 989 | 885 | 683 | 434 | 372 | 372 | 2.66倍 |
| **60分** | 1000 | 885 | 683 | 916 | 753 | 753 | **1.46倍** |
| 90分 | 1000 | 885 | 683 | 1000 | 955 | 955 | 1.46倍 |

   60を超えても律速が賢さ（インプット3h）に移るだけで差は縮まらないので、60で止める。
   （この表は旧カーブ `GROWTH_K=6.968` で測ったもの。`3.5` では 60分のとき
   スピード648・スタミナ448・賢さ413 で最大/最小 1.57倍と、比はほぼ同じ。）

⭕ 残る1.46倍は「インプットに割く時間が開発の半分」という**実際の配分がそのまま出た差**
   なので、これ以上は定数で潰さない。偏りが気になるなら、次は活動ごとに「週あたりの
   基準時間」を置いて正規化する（案B）。

## 5. レースシミュレーションのモデル

**実装済み**（`race_sim/engine.py`）。走破タイムを先に決め、そこから区間ラップと
通過順を逆算する。

```
レース基準タイム = コース基準(実測) + 馬場補正(実測) + レース単位のブレ
各馬のタイム     = レース基準タイム - 実力差(秒) + 個体のブレ + 不利
区間ラップ       = 脚質ごとの配分テンプレート × タイム
```

⭕ 当初は速度と消耗を1歩ずつ積み上げる物理シミュレーションを設計していたが、その形だと
   パラメータから結果までの経路が長く、走破タイム・着差・勝率の分布を実測に合わせ込むのが
   非常に難しい。タイムを先に決める形なら較正目標を直接狙える。展開の説得力は区間
   テンプレートが担保する。

⭕ **クラス補正はタイムに入れない**。「上のクラスほど基準タイムが速い」と「上のクラスほど
   強い馬が集まる」を両方入れると二重計上になる。クラスの差は出走馬の能力水準だけで表す。

実装されている効き方：

- **ペース**は脚質構成で決まり、逃げ馬が複数いると競り合って上がる。ハイペースなら差し・追込が有利
- **賢さ・瞬発力はメンバー内の相対値**で効く。絶対値で効かせると上位クラスほど堅くなる歪みが出た
- **不利・出遅れ**が6%で発生し、賢い馬ほど受けにくい
- **距離区分**で能力の重みが変わる（短距離はスピードと瞬発力、長距離はスタミナ）。ダートはパワーの比重が2倍

### 較正の結果（2026-09-10時点）

実データ2018〜2026年・26,052レースを基準に、`tools/calibrate.py --pool` で検証した。
**ライバル馬プールから実際に組んだ出走表**での数字（クラス別に540レース）。

| 目標 | 実測 | シミュレーション |
|---|---|---|
| 勝ちタイム（基準との差） | 0 | -0.20〜+0.01秒 |
| 勝ちタイムの標準偏差 | 1.06秒 | 0.88〜1.01秒 |
| 上がり3F（基準との差） | 0 | -0.11〜-0.07秒 |
| 上がり3Fのばらつき | 0.70秒 | 0.59〜0.61秒 |
| 1着-2着の着差 中央値 | 0.20秒 | 0.18〜0.21秒 |
| 1着-2着の着差 90%点 | 0.60秒 | 0.53〜0.63秒 |
| 能力最上位の勝率 | 32.7% | 27.4〜36.5% |
| 能力最上位の複勝率 | 64.1% | 56.9〜69.4% |

**既知のずれ**: 脚質シェアの先行が21.1%（実測25.5%）、追込が38.5%（実測33.9%）。
シミュレーション側は通過順を厳密な順位として扱うが、実際の成績表には同順の通過順が
含まれるため、上位の順位が実測ではやや圧縮される。定義の差であり、モデルの誤りではない。

較正の過程で分かった、モデルに反映済みの実データの性質：

- **馬場が渋ると芝は遅く、ダートは速くなる**（芝の不良は+3.68秒、ダートの不良は-1.57秒）
- **上がり3Fの水準はクラスより「コース」で決まる**。区間テンプレートから導いていたとき、
  ずれはクラス方向ではなくコース方向に並んだ（東京芝2400で+2.3秒、ダートで-0.3〜-1.0秒）。
  芝とダートで上がりは2秒以上違い、同じ芝でも距離で変わる。走破タイムと同じく、
  実測のコース別平均を基準に据えることで解決した
- **道中の位置は絶えず入れ替わる**。区間配分を脚質だけで決めると、同じ脚質の馬の
  通過順が「6-6-6-6」と道中まったく動かない。区間ごとに小さな揺れを入れている
  （合計は変えないので着順には影響しない）
- **レース内の上がり3Fのばらつき**は芝でSD0.86秒、ダートで1.13秒。脚質による区間配分の
  差をそのまま使うと芝でSD1.24まで広がり、後方の馬が非現実的な差し切りを見せた。
  差の強さを芝0.70・ダ0.88に絞って実測に合わせている（`STYLE_SHAPE_SCALE`）

## 6. ライバル馬プール

`race_sim/rivals.py` が `data/rivals.json` から出走表を組む。プールは
`tools/build_rivals.py` が実データから生成する（2,683頭、890KB）。

### 実在馬を「プロフィールの形」として使う

⭕ 能力・脚質・適性をそれぞれ独立に抽選すると、「ダート短距離の追込馬でスタミナが高い」
   のような実在しない組み合わせが量産される。そこで5走以上の実在馬24,403頭から
   **どの馬場・距離を、どの位置取りで、どのクラスで走ったか**というプロフィールを
   テンプレートとして抜き出し、そこに架空の名前と能力値を与えている。個体は特定できない
   （同じプロフィールの馬が何千頭もいる）一方、条件どうしの相関は実データのまま残る。

馬名は実在馬名の字面から学習した2次のマルコフ連鎖で生成し、実在の馬名・種牡馬名・
母父名（46,424件）と突き合わせて衝突を除く。血統名も同じ方法で架空のものを作る。

### 脚質はレースごとに決まる

⭕ 馬に固定の脚質を持たせる形を最初に試したが、実データでは位置取りの個体内SD(0.226)が
   個体間SD(0.169)より大きく、脚質は固定の属性ではなく傾向でしかない。さらに通過順は
   **レース内の順位**なので、分布は構造上どの馬も一様になる（逃げ＝先頭1頭＝約7%）。
   個体ごとに正規分布で引いたときは中央に寄り、差しが41%（実測33%）に膨らんだ。

いまは出走各馬の位置取りを引いたうえで**メンバー内で順位づけ**して脚質を決める。
実際のレースと同じ手順なので、シェアは定義上そのまま再現され、逃げ馬は必ず1頭になる。
プレイヤーが宣言した脚質は「意思」であり、**約84%で通り、残りは他馬に前を取られる**。

⭕ ライバルの意思のブレは、保存してある位置取りのばらつきの0.6倍を使う。`pos_sd` は
   キャリア全体で観測された値で、そこには「他馬が行かせてくれたか」という結果が既に
   含まれている。そのまま毎レースの意思として使うと全馬が高頻度でハナを主張し、
   逃げの宣言が通るのが半分（52%）まで落ちた。

### 組めない番組がある

⭕ JRAにダートのG2はほぼ無いため、プールにもG2のダート馬はいない。それでもダートG2を
   組むと芝の馬が適性ペナルティを背負って動員され、勝ち時計が1.05秒も遅くなった。
   `rivals.is_supported(race)` がその条件を組めるかを返すので、番組を組む側（Phase 5の
   レース番組表）は必ずこれを見ること。

## 7. 再生ビューア

`race_sim/viewer.html` が結果JSONを読んでレースを再生する。外部ライブラリを一切使わず、
canvas 2D と標準のDOMだけで動く。`tools/make_viewer.py` が結果を埋め込んだHTMLを書き出す
（1レースぶんで約39KB）。

**後方から追走するカメラ**で、走路が奥へ抜けていく3D視点。ピンホール投影で、走路上の
（距離, 横位置）を画面座標に落としている。

- 位置は**区間タイムから補間**する。区間の中は等速とみなす
- **走路は実際の競馬場の楕円**。JRA各競馬場の「回り」「ゴール前直線」「1周距離」（芝）を
  持ち、直線2本＋半円のコーナー2つで近似する。1周距離と直線が分かればコーナー半径が
  決まる。レースは必ずゴール（ホームストレッチの終点）で終わるので、距離を逆算すれば
  スタート位置が決まり、道中でコーナーを回って最後に直線を向く形になる
- 走路の曲がりは**カメラから先の曲率を2回積分した横ずれ**で描く。コーナーでは走路が
  横へ流れ、直線に入ると正面を向く
- 隅にコースの**全体図**を出し、馬群が1周のどこにいるかを示す
- 奥行きに応じて馬の大きさと画面上の高さが決まる。走路は緩くカーブし、外に木が並ぶ
- 馬は後ろから見たかたちで描き、**騎手の勝負服を枠色**にする（JRAの実際の配色：
  1白 2黒 3赤 4青 5黄 6緑 7橙 8桃。枠は均等割りで余りを外枠から1頭ずつ足す）
- **毛色**は鹿毛45% / 黒鹿毛20% / 栗毛20% / 芦毛8% / 青鹿毛5% / 栃栗毛2% の実際の割合に
  沿って、馬名から決定的に決める
- 左に隊列のオーバーレイ、大きな残り距離と経過時間、下に実況テキスト

⭕ **馬番1が最内。** 内側は右回りなら画面の右、左回りなら左になる。当初これを逆に
   していた。

⭕ **遠近をつけると着差が目で読めなくなる。** 正確な差は左の隊列オーバーレイと、
   平面図で見る「全体」カメラが担う。走路の側は見て楽しむことに振り切っている。

⭕ コーナーでは遠方の走路が画面外へ流れる（東京のコーナー半径は約164m）。実際の中継でも
   コーナーの先は見えないので、画面から外れたところで描画を打ち切っている。

⭕ カメラは走路の内側へ7mずらしてある。中央に置くと馬群が画面の左右いっぱいに広がり、
   左の隊列オーバーレイと重なって両方見づらくなった。

⭕ テンプレートは `<html>` や `<head>` を持たない**断片**の形にしてある。Artifactとして
   公開するときはこの形でなければならず、ブラウザで直接開く用途では make_viewer.py が
   完全なHTML文書に包む。

⭕ 結果JSONは `<script type="application/json">` に埋め込む。中の `</` をエスケープしないと、
   馬名やレース名に `</script>` が入ったときにブロックが途中で閉じてページが壊れる。

### 後回しにした作り込み

ビューアは結果JSONだけを入力に取り、エンジンにもBotにも参照されていない。全面的に
描き直しても影響範囲はこのファイル1枚に閉じるので、**作り込みは後からで安全**。

やりたいこととして挙がっているもの：

- 内回り・外回りの描き分け（いまは競馬場ごとに代表の1つを使っている）
- 芝の削れた跡、砂煙、蹄跡
- ゴール前でカメラが横に回り込む演出／僅差のときのスロー再生
- 馬体の描き込み（いまは簡略なシルエット）
- 実況の語彙を増やす

⭕ ただし**レース条件の `race` 辞書に何を持たせるか**だけは、Phase 4 で番組表を作るときに
   決めるのが安い。内回り／外回りの区別、開催回次、重賞の格といった情報は番組表が
   生み出す側にある。`race` はそのまま結果JSONへ流れ、ビューアは知らないキーを無視するので
   後から足しても壊れないが、番組表を書くついでに入れておくほうが手戻りがない。

## 8. 世代交代

**20戦で引退**（週2開催なので現役は約10週＝2.3か月）。牡なら種牡馬、牝なら繁殖入りし、
次世代の初期能力に血統補正が乗る。前世代の成績と、上限を超えて積んだぶんが補正になる。

⭕ **将来の「配合」を見据えて、血統は名前だけで持たない。** 引退馬は能力・成績・適性を
   持った実体として `stable.json` に残す。名前だけの飾りにしておくと、配合（父と母の
   組み合わせで仔の能力・適性を決める、インブリードやニックスを見る）を足すときに
   データ構造から作り直すことになる。20戦・10週という比較的短い弧を選んだのも、
   世代交代を多く回して配合を楽しむためである。

### 配合

配合前の世代交代は「親1頭の積み上げ×10%×種牡馬価値」を初期値にするだけで、**適性は
毎回ランダム**だった。長距離が得意なG1馬を作っても次の代がスプリンターになる。配合の
狙いは**適性を血で繋ぐ**ことにあり、能力の初期値は副次的なものとする。

**決定事項（2026-09-11）**

| 論点 | 決定 |
|---|---|
| 相手の出所 | 自分の引退馬（異性・無料）＋ 市場（ライバル馬プールから生成・賞金で払う） |
| 能力の初期値 | 両親の積み上げ（分）の平均 × `INHERIT_RATE` 10% × 両親の種牡馬価値の平均 |
| 適性の遺伝 | 項目ごとに父か母から半々で受け継ぎ、15%で1段ずれる（A〜Dの範囲内） |
| タイミング | **15戦目から予約**でき、引退した瞬間に予約どおりの仔が生まれる |

⭕ **現役馬は必ず片親になる。** 「自分が育てた馬の仔」が情緒の核なので、引退馬同士・
   市場馬同士の配合は作らない。現役馬が牡なら相手は牝、牝なら牡。

⭕ **引退時ではなく現役中に予約する**のは、調教を止めないため。引退の瞬間に選ばせると
   選ぶまで現役馬が居らず、その間に記録した活動が誰の成長にもならない。予約が無ければ
   従来どおり相手なしで世代交代する（後方互換）。

**市場**

- 現役馬と異性の馬を**6頭**提示する。下級（未勝利〜2勝）・中級（3勝〜G3）・上級（G2〜G1）
  から2頭ずつ。セン馬は除く
- 現役馬の `id` をシードにするので、**同じ世代のあいだ市場は変わらない**（見るたびに
  入れ替わると比較できない）
- 能力はプールのまま。G1級で平均658・最大775なので、G1を勝ち続けた自分の引退馬
  （900前後）のほうが強い。**市場の価値は能力ではなく「欲しい適性」と「異性が居ない
  世代の穴埋め」**。序盤の世代は自分の引退馬も弱いので、そこでは能力でも市場が勝る
- 種付け料 ＝ そのクラスの1着賞金 × `STUD_FEE_RATIO` 1.5（G1 22,500万・OP 3,300万・
  未勝利 780万）。賞金表に連動させるので、賞金を調整しても比率は保たれる

⭕ 1世代（20戦）の獲得賞金は、難易度 `GROWTH_K=3.5` で **普通 1.5億・良い 4.5億・
   最良 12億**。G1種牡馬の2.25億は「良い世代の収入の半分、普通の世代1.5頭分」の水準。
   **この収入は難易度で変わる**ので、`GROWTH_K` を動かしたらこの比率を基準に
   `STUD_FEE_RATIO` を直す（当初は 5 だったが、係数 6.968 時代の12〜20億が前提だった）。

**資金**

賞金はこれまで馬の `record['prize']` に貯まるだけで使い道が無かった。厩舎の `funds`（万円）
を足し、レース賞金は成績と資金の両方へ入る。**`load_stable()` で `funds` が無ければ
現役馬と引退馬の賞金の合計で補う**（読み込み時移行の流儀）。種付け料は予約時に引き、
予約を取り消せば戻す。

**資金の出口は2つ**：種付け料（世代に1回・大きい）と遠征費（出走ごと・小さい）。

| 競馬場 | 遠征費 |
|---|---|
| 東京・中山（地元・美浦所属の想定） | 0 |
| 福島・新潟 | 80万 |
| 中京・京都・阪神 | 150〜200万 |
| 札幌・函館・小倉 | 300万 |

⭕ 遠征費は**クラスに関わらず一定**（実態どおり）。未勝利の4着賞金（78万）より高いので
   序盤は行き先で損得が出るが、G1級になれば誤差になる。**番組表には遠征費0の地元レースを
   必ず1本入れる**（`calendar.offers()`）ので、資金が無くても出走の手段は残る。
   出走登録時に引き、取り消し・取り直しで戻す。

**血統表**

`pedigree` を `{'sire': 名前, 'dam': 名前}` の平面から、`{'name', 'sire': node, 'dam': node}`
の**再帰ノード**へ変える。市場馬はプールが `sire`（父）と `bms`（母父）を持つので、
`{'name': X, 'sire': {'name': 父}, 'dam': {'name': '－', 'sire': {'name': 母父}}}` として
3代を持たせる。保存時は4代で打ち切る。

⭕ インブリード（3×4など）とニックス（父系×母父系の相性）は**後回し**。血統表が
   3〜4代必要で、自分の馬は年5〜6世代しか回らないので、効いてくるのは運用1年後。
   構造だけ先に持ち、上の基本形が回ってから足す。

**UI（`ui_horse`）**

厩舎メニューに「🧬 配合」。15戦未満なら押せない（あと何戦で開くかを出す）。
セレクトで相手を選ぶ → 費用を確認して予約 → 仔の名前を入れるモーダル（空欄なら自動）。
モーダルには `TextInput` しか置けないので、相手の選択はモーダルの前に置く。
`format_horse()` に資金と配合予約を表示する。CLI（`tools/play.py`）にも `breed` を足す。

## 10. 定期配信への組み込み

`@tasks.loop(time=DELIVERY_TIMES)` は1つだけ、という既存ルールを守る。

- 出走登録：いつでも可能。**今のクラスと適性に合う3〜4レースから選ぶ**
  （`rivals.is_supported()` を満たす条件だけを提示する）
- 開催日の朝8:00：**出走登録の有無を知らせる**（`horse_logic.format_race_day_notice()`）
- 開催：**土曜と水曜の20:00**（夜の分岐に相乗りし、曜日で判定する）
- 結果の再掲：月曜朝の週間サマリー内（その週の2戦をまとめて）
- `/test_race` を用意し、時刻を待たずに動作確認できるようにする（`/test_reminder` と同じ流儀）

⭕ **朝の告知は「登録し忘れに気づく」ためだけにある。** レースは20:00に自動で走るので、
   登録が無いと何も言われずに開催日が過ぎ、現役10週のうち1戦をまるごと失う。
   登録があれば発走時刻の確認、無ければその日の番組表を添えて警告する。

⭕ `run_entry()` は**登録の日付を見ない**。Botが落ちていて20:00を跨いだ場合、前回の登録が
   残ったまま次の開催日の夜に走る（古いレースとして実行される）。黙ってそうなると面食らうので、
   **登録の日付が今日かどうかで文言を分ける**。取り直せば今日の番組から選べる。

## 12. テスト方針

既存の流儀（CLAUDE.md「テスト」節）に従う。

- エンジンは seed 固定で決定的 → 期待値との一致をユニットテストで検証
- 分布のテストは別途「1000回走らせて平均タイムが基準±0.5秒」の形で書く
- データファイルのパスはモジュールレベル定数にし、テストでは `monkeypatch.setattr` で差し替える
- `horse_logic` が複数ファイルを読む場合は**そのすべて**を差し替える
- 日付に依存する関数は `today` / `now` を省略可能な引数で受け取る
